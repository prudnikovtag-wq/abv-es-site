# Регламент: сайт abv-es.ru (АБВ Электросервис)

Это репозиторий статичного сайта **abv-es.ru** — сервисный центр и склад оборудования ABB.
Сайт — обычные HTML/CSS/JS-файлы, лежат на хостинге reg.ru. Серверного кода нет.

## Главные правила (нарушать нельзя)

1. **На сайт выкладывает только сценарий «Выкатка на сайт» (GitHub Actions), и запускает его только владелец**
   кнопкой Run workflow. У нас нет и не должно быть паролей от хостинга: они лежат в секретах GitHub
   (`FTP_HOST`, `FTP_USER`, `FTP_PASSWORD`; FTP-пользователь `u2003889_deploy` ограничен папкой `/www/abv-es.ru`).
   Никогда не добавлять другие способы запуска выкатки (по пушу, расписанию и т.п.) и не просить у владельца пароли.
   **Не создавать и не менять ничего в `.github/` без прямого поручения владельца** — любой workflow в любой
   ветке получает доступ к секретам хостинга. Значение `FTP_HOST` — строго `server247.hosting.reg.ru`
   (на это имя выписан сертификат; IP или abv-es.ru не пройдут проверку FTPS).
2. **Репозиторий = точная копия того, что лежит на хостинге.** Пути файлов в репозитории
   совпадают с путями на сайте. Ветка git `na-saite` указывает на версию, которая сейчас на сайте (именно ветка, не тег: теги через прокси не отправляются).
3. **Без пройденных проверок правка дальше не идёт.** Ни демо, ни файлы владельцу.
4. **Не отправлять заявки через формы.** Форма заявки шлёт письма на рабочую почту
   (formsubmit.co → help@abv-es.ru). Тестер проверяет форму только с заблокированной отправкой
   (так уже настроено в `tools/screens.mjs`).
5. **Не трогать то, о чём не просили.** Нашли постороннюю проблему — записать в отчёт и в `BOARD.md`
   в колонку «Идеи / найдено», но не чинить в этой же правке.
6. Не менять счётчик Яндекс.Метрики (id 92958095), реквизиты, телефоны, почты и цены,
   если задача прямо об этом не говорит.

## Как устроен сайт

- Корень: страницы разделов — `index.html`, `about.html`, `services.html`, `sklad.html`,
  `contacts.html`, `projects.html`, `partners.html`, `obuchenie.html`, `retrofit*.html` и др.
- `tovar-<артикул>.html` — карточки товаров склада (на них ссылается каталог `sklad.html`).
- Старые адреса `/<артикул>.html` и `/sklad/<артикул>.html` переадресуются (301) на `tovar-<артикул>.html`
  правилами в `.htaccess`; проверка — `python3 tools/check_redirects.py`. Файлов-артикулов в корне быть не должно.
- `images/*.html` и `images/feed.xml` — случайные копии, сайт на них не ссылается.
- `promo/` — отдельная промо-страница со своими `css/`, `bootstrap/`, `assets/`.
- Стили: `css/style.css`, `css/media800.css` (мобильная версия до 800px). Шрифты — Google Fonts.
- Скрипты: `menu.js` (меню; **файл в кодировке windows-1251** — при правке сохранять в ней же
  или сознательно перевести в UTF-8, кириллица там только в комментариях; подключается с `?v=ДАТА` для сброса кеша), `headload.js`,
  `request-form.js` (форма заявки), `reveal.js` (анимации появления), `slider.js`.
- `feed.xml` — товарный фид для Яндекса. Меняется только вместе с товарами.
- `docs/` — PDF с документами компании. Не трогать.
- **Если меняется CSS или JS — поднять версию `?v=ГГГГММДД` во всех страницах, где он подключён**,
  иначе у посетителей останется старая версия из кеша.

## Команда и роли

Основная сессия — **оркестратор**. Она не пишет код сама, а ведёт задачу:

| Роль | Файл | Что делает |
|---|---|---|
| Вёрстка | `.claude/agents/verstka.md` | правит HTML/CSS/JS по задаче |
| Ревизор | `.claude/agents/revizor.md` | только читает: ищет ошибки, риски, побочные эффекты; сам не чинит |
| Тестер | `.claude/agents/tester.md` | открывает страницы в браузере (телефон и компьютер), делает скриншоты, ловит ошибки |

Если в задаче несколько независимых частей (например, разные страницы), можно запустить
несколько «вёрсток» параллельно — каждой свои файлы, чтобы они не правили одно и то же.

## Начало каждой сессии

Если репозиторий клонирован заново (новая сессия): `git fetch origin na-saite:na-saite` — иначе
`tools/package.sh` не узнает, что сейчас на сайте. Скрипты: `python3`, `node` и playwright
(глобальный или `npm i`).

## Порядок работы над задачей

Доска задач — файл `BOARD.md`. Колонки: **В работе → Проверка → Демо → Готово к выкатке → На сайте**.
Также веди список задач (виджет) в сессии — его видит владелец в приложении.

1. **Понять задачу.** Если непонятно, что именно хочет владелец, и ошибка дорого стоит — спросить
   одним коротким вопросом. Иначе — выбрать разумный вариант и написать, какой выбран.
2. Создать ветку `zadacha/<коротко>` от `main`. Карточка в `BOARD.md` → «В работе».
3. **Вёрстка** вносит правку.
4. **Проверка** (карточка → «Проверка»):
   - `python3 tools/check_site.py <изменённые страницы>` — должно быть **0 новых ошибок**
     (сравнить с тем, что было до правки: старые ошибки не считаются новыми);
   - **Ревизор** читает дифф (`git diff main`), выносит вердикт «ПРОПУСКАЮ» или «НЕ ПРОПУСКАЮ» с причинами;
   - **Тестер** запускает `node tools/screens.mjs <страницы>` и смотрит скриншоты глазами:
     телефон 390px и компьютер 1440px.
   - Если ревизор или тестер не пропустили — вернуть вёрстке с их замечаниями. Повторить.
5. **Демо** (карточка → «Демо»). Опубликовать изменённые страницы как приватную ссылку (Artifact):
   - `python3 tools/demo_files.py --copy <страницы>` — копирует страницы и всё, что они подключают,
     в `out/demo/` (без счётчика Метрики, SVG без DOCTYPE, JS/CSS в UTF-8) и печатает список файлов;
   - публиковать: `file_path` = `out/demo/<главная из изменённых страниц>`, `root` = `out/demo`,
     `files` = остальные пути из списка;
   - одна и та же задача — одна и та же ссылка (обновлять, а не плодить новые).
   Отчёт владельцу: что изменено (по-человечески, без кода), что проверено, скриншоты «было / стало»,
   ссылка на демо. Спросить: «Выкатываем на сайт?»
6. Правки по замечаниям владельца — снова через шаги 3–5.
7. **Выкатка** — только после явного согласия владельца («выкатывай», «да, на сайт»):
   - слить ветку в `main`, отправить `main` в GitHub; карточка → «Готово к выкатке»;
   - написать владельцу: что именно уйдёт (вывод `bash tools/changes.sh`) и попросить запустить
     **Actions → «Выкатка на сайт» → Run workflow → режим `vykatka`** (можно сначала `proverka`);
   - сценарий сам: сверит сервер с репозиторием, остановится, если файлы на сервере меняли вручную,
     сделает резервную копию, загрузит, проверит, при ошибке откатит, и сдвинет ветку `na-saite`;
   - после выкатки — открыть изменённые страницы на живом сайте (WebFetch) и доложить; карточка → «На сайте».
   - если отчёт сценария говорит «ручные правки на сервере» — НЕ обходить: скачать с сервера эти файлы
     (попросить владельца прислать), закоммитить в main как «Синхронизация с сайтом», сдвинуть `na-saite`, повторить;
   - если выкатка прервалась (отмена, таймаут) и в отчёте нет строки об откате — попросить владельца запустить
     `proverka`: она покажет расхождения; при необходимости вернуть файлы из артефакта `vykatka-N` (резервная копия);
   - при правках `tools/deploy.sh` — прогнать имитацию (fake lftp) и отдать ревизору; первый запуск после правки — только `proverka`.
   Запасной путь (если владелец хочет загрузить сам): `bash tools/package.sh` → файлы/zip + `СПИСОК.txt`,
   после его «залил» — `git branch -f na-saite main && git push -f origin na-saite`.

## Если сайт поменяли не через нас

Владелец может загрузить файл на хостинг сам. Тогда он присылает новый файл (или всю папку) —
положить в репозиторий по тому же пути, коммит «Синхронизация с сайтом», ветку `na-saite` → на этот коммит.
Перед любой задачей спросить себя: точно ли `main` совпадает с сайтом? Если сомнение — спросить владельца.

## Тексты и стиль

- Язык сайта — русский, деловой, без канцелярита. Термины ABB — как в каталоге ABB.
- Сохранять существующий визуальный стиль сайта (цвета, шрифты Montserrat / Open Sans / Roboto Condensed).
- Отчёты владельцу — простым языком, коротко. Владелец не обязан читать код.
